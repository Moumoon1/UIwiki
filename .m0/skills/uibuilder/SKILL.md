# Figma 组件页面构建器

## 核心规则

不要从零设计新页面。先判断用户需求是 B 端还是 C 端，再从 `wiki/index.md` 进入知识地图，复用最接近的页面模式或用户明确给出的组件顺序，并保留布局、密度、层级、组件顺序和交互模型，除非用户明确要求改变工作流。

每一个可见 UI 区域都必须映射到对应端组件目录中的已批准组件。如果没有完全匹配的组件，复用最接近的已批准组件，并在 `component_gaps` 中列出差距；不要悄悄创造新的 UI。

不要编造用户没有提供的业务文案、活动规则、奖励金额、版权要求、FAQ、二维码内容或示例数据。页面模式可以固定模块和顺序，但模块内容必须来自用户需求、现有参考页面、Figma 组件默认内容或明确标记的占位符。

使用 Figma 组件时，必须插入组件实例并保持实例内部结构和样式不变。不要 detach instance、重绘组件、复制组件内部图层，或修改组件内部的 Auto Layout、padding、gap、radius、shadow、fill、stroke、font 和图层顺序。

每个页面模式的“锁定结构”就是该页面允许出现的唯一模块白名单。除非用户明确要求新增模块，否则不得新增 section、卡片、CTA、说明区、装饰区、状态区或任何锁定结构之外的可见模块。

C 端页面画布宽度固定为 `414px`，模块之间的外部间距固定为 `16px`。头图、吸底/底部按钮等标记为全宽的组件保持 `414px` 宽，不加左右页面边距；普通卡片区域使用 `16px` 左右外边距，内容区目标宽度为 `382px`，并在页面内水平居中。这些值只用于页面外部布局，不得通过修改组件内部 padding、gap 或 Auto Layout 来实现。

C 端页面必须创建一个 `414px` 宽的顶层页面 Frame，并使用纵向 Auto Layout 排列模块。所有页面模块必须作为同一个顶层页面 Frame 的直接子级，按页面模式或用户给定顺序从上到下排列，并在父级 Frame 内水平居中；不得把模块插入后停留在同一坐标、绝对定位堆叠，或让模块脱离父级 Auto Layout。

## B/C 端入口判断

处理任何需求时，第一步先判断 `audience_type`：

- `b端`：面向企业内部角色、管理员、运营、销售、财务、HR、客服、审核员、配置人员、商家后台或 SaaS 工作台的页面。
- `c端`：面向普通用户、活动参与者、报名用户、内容读者或移动 App 用户的页面。
- `不确定`：用户只说“做一个页面”且没有角色、业务对象或使用场景时，先根据关键词和主要工作流做合理判断；如果会显著影响结构，追问 1 个澄清问题。

默认分流规则：

- 出现管理、审核、审批、配置、后台、列表、权限、角色、订单处理、数据看板、工单、SaaS、运营等词，走 B 端模式。
- 出现报名、活动报名、政策、奖励、激励、参与、任务、作品、抽奖、榜单、收益、排行、关注我们等词，走 C 端模式。
- 同时包含 B 端和 C 端时，以目标使用者为准；例如“给运营配置 C 端活动页的后台”是 B 端，“给用户看的活动页”是 C 端。

## 必需工作流

0. 从 `wiki/index.md` 进入 LLM Wiki 知识地图，按当前需求只读取相关页面。运行时以 Wiki 为唯一权威来源。
1. 将用户需求解析为产品意图、用户角色、目标端类型、主工作流、数据对象、操作、状态和约束。
2. 判断 `audience_type` 是 `b端`、`c端` 还是 `不确定`，并选择对应端的页面模式。
3. 如果是 B 端，阅读 Wiki 中的 B 端页面模式；如果是 C 端，阅读 Wiki 中的 C 端页面模式。按工作流而不是只按视觉标签选择最接近的现有公司页面模式。
4. 阅读所选模式的详情，并保留其锁定结构、密度、操作位置、组件顺序和布局节奏。
5. 将所选模式的锁定结构作为默认模块白名单。如果用户明确给出页面或组件顺序，且所有模块都能映射到 Wiki 组件目录中的已批准组件，优先按用户顺序走轻量拼接模式；否则按页面模式锁定结构走完整规格模式。
6. 如果是 B 端，阅读 `wiki/components/b/component-catalog.md`；如果是 C 端，阅读 `wiki/components/c/component-catalog.md`。把每个页面区域映射到已批准的 Figma 组件。
7. C 端组件目录使用一个 Figma 组件源链接和模块映射表；先读取 Figma 源，再按模块名、别名和结构匹配真实组件。
8. 实现布局、间距、设计 token、响应式行为或前端代码时，只阅读 Wiki 中对应端的布局、token 和组件说明规则。
9. 最终确定前阅读 Wiki 中对应端的反模式和校验清单，移除任何通用 AI UI、过度模板化 UI、装饰性 UI 或偏离品牌的组合方式。
10. 轻量拼接模式下，只在内部维护 `audience_type` 和 `sections` 清单，不输出、不保存完整 page spec JSON；直接创建目标 Frame 并插入组件实例。
11. 完整规格模式下，生成符合 `assets/page-spec-schema.json` 的页面规格作为中间施工清单；不要把 JSON 当作最终交付物。props 中不得填入臆造业务内容，缺失内容使用 `TODO`、`待用户提供` 或保留组件默认内容。
12. 生成 JSON 规格时，使用 `scripts/validate-component-usage.js` 校验页面规格。
13. 如果当前环境可用 Figma MCP、Figma 插件或其他画布编辑工具，必须继续把页面落到 Figma 画布：创建目标 Frame，按 `sections` 顺序插入或复用对应 Figma 组件实例，写入 props 文案，设置变体，排列布局、间距和状态。
14. 画布交付前必须检查所有可见模块仍然是 Figma component instance，且没有被 detach、重绘或修改内部样式；不满足则视为失败，并写入 `component_gaps` 或交付说明。
15. 最终交付物必须是画布上的设计稿；最终输出必须包含画布位置或链接、目标端类型、匹配的页面模式或用户顺序、组件映射、允许的差异、组件缺口和校验结果。
16. 只有在当前环境没有可用画布工具时，才允许退化为输出页面规格 JSON 或明确搭建步骤，并说明尚未完成画布落地。

## 匹配策略

优先选择同一端内、用户工作流最接近需求的公司页面模式。

B 端通常匹配：

- 管理、列表、审核、审批、配置类需求通常映射到管理列表模式。
- 创建、编辑、详情类工作流通常映射到表单、详情或抽屉模式。
- 监控、KPI 和运营概览类需求通常映射到仪表盘模式。
- 入门、设置或引导式配置类需求通常映射到向导模式。

C 端通常匹配：

- 报名、活动报名、资料提交、表单收集类需求通常映射到 C 端报名页模式。
- 政策说明、活动规则、奖励政策、参与说明类需求通常映射到 C 端政策介绍页模式。
- 用户参与活动、做任务、提交作品、抽奖、查看收益类需求通常映射到 C 端活动页模式。
- 排名、榜单、收益排行、作品排行、邀请排行类需求通常映射到 C 端榜单页模式。
- 如果用户明确给出卡片模块顺序，优先按用户顺序组合；没有给出时，按 Wiki 中对应模式的锁定结构组合。

## 轻量拼接模式

当需求满足以下条件时，使用轻量拼接模式：

1. 用户已经明确要哪些页面，或明确给出页面内模块/组件顺序。
2. 页面只是把已批准组件在同一个画布 Frame 内纵向排列。
3. 每个模块都能在对应 Wiki 组件目录中找到已批准组件。
4. 不需要记录复杂业务规则、状态矩阵、组件缺口或交付给他人复用的规格文件。

轻量拼接模式不得输出或保存完整 `*-spec.json`。AI 只在内部维护最小清单：`audience_type`、页面名称、按顺序排列的组件名、全宽/内容区布局标记，然后直接落 Figma 画布。

只要出现以下任一情况，升级为完整规格模式：需要 AI 推断页面模式、存在组件缺口、需要新增锁定结构之外模块、包含复杂业务规则或状态、需要严格验收清单、用户明确要求规格文件或当前没有可用画布工具。

当多个模式都可能适用时，选择对不可变结构改动最少的模式。如果没有模式适配该工作流，说明需要新模式，并基于现有组件提出最小的新模式。

## 相似性契约

每个生成页面都必须包含相似性契约：

- `same_shell`
- `same_header_structure`
- `same_primary_action_placement`
- `same_filter_or_control_position`
- `same_main_content_density`
- `same_state_model`
- `changed_only_domain_content`

任何 `false` 值都必须附带简短原因，并且必须关联到用户需求。

## 实现策略

可见 UI 只能使用已批准组件。自定义代码只能用于连接数据、排列已批准组件或接入交互。

允许：

- 领域相关的标签、表格列、表单字段、空状态文案和行操作。
- 选择组件已有 variant，填写组件暴露出来的 text override、image override、props 或数据绑定。
- 调整不同组件实例之间的外部间距，前提是符合匹配页面模式和布局规则。
- 修改组件实例的宽度或约束，前提是该组件本身支持响应式或 resize。
- 目标框架所需的布局胶水代码，前提是不创建新的视觉组件。
- 当应用代码库已经采用该模式时，可围绕已批准组件添加轻量适配层。

禁止：

- 用任意 HTML/CSS 重做目录中已有的组件。
- detach Figma component instance。
- 修改组件实例内部 Auto Layout、padding、gap、radius、shadow、fill、stroke、font、图层顺序或内部约束。
- 移动、删除、新增组件内部图层，或复制组件内部图层后手工拼装。
- 为了适配页面而改组件内部结构；如果需要内部变化，必须写入 `component_gaps`。
- 编造用户未提供的活动文案、奖励规则、版权声明、FAQ、榜单数据、二维码信息或联系方式。
- 新增锁定结构之外的可见模块、section、卡片、CTA、说明区、装饰区或状态区。
- 新增装饰性区块、营销式首屏、大尺寸卡片、渐变、插画、自定义阴影或自定义圆角。
- 在没有明确用户需求的情况下，改变匹配模式中的 shell、页头、表格密度、筛选位置或操作位置。

## 模块白名单规则

每个页面模式的锁定结构是默认模块白名单。没有用户明确顺序时，`sections` 必须按锁定结构逐项生成，不能多、不能少、不能换顺序。用户明确给出组件顺序且全部组件已批准时，按用户顺序生成，并在交付说明中标记为轻量拼接模式。

如果用户明确要求增加锁定结构之外的模块：

1. 优先判断是否应匹配另一个已有页面模式。
2. 如果仍需新增，必须使用已批准组件。
3. 必须在 `similarity_contract.exceptions` 说明原因。
4. 必须在 `component_gaps` 记录它偏离了原页面模式。

不要为了让页面更完整、更好看或更像活动页而自行添加模块。

## 组件实例锁定规则

组件库组件必须作为 Figma component instance 使用。使用组件不等于“画一个看起来像组件的区域”，而是必须插入真实组件实例，并通过组件允许的变体和 override 完成配置。

允许修改的范围：

1. 选择已有 variant。
2. 修改组件暴露的文字、图片、状态、数据和 props。
3. 调整组件实例之间的外部布局和间距。
4. 在组件支持的范围内调整实例宽度、约束或响应式行为。

禁止修改的范围：

1. detach instance。
2. 修改组件内部 Auto Layout、padding、gap、radius、shadow、fill、stroke、font。
3. 移动、删除、新增或重排组件内部图层。
4. 复制内部图层并手工重画组件。

如果用户需求必须改变组件内部视觉或结构，不能直接改组件。应选择最接近的已批准组件，并在 `component_gaps` 中记录需要设计系统新增或调整的能力。

## C 端画布与间距

C 端页面必须使用以下固定外部布局参数：

- 画布宽度：`414px`
- 普通卡片内容区左右外边距：`16px`
- 模块之间外部间距：`16px`
- 内容区目标宽度：`382px`
- 全宽模块：`Campaign/HeroImageCard`、`Campaign/bigButton`、`Consumer/panel` 等明确为头图、底部按钮、吸底按钮、底部弹出面板的模块保持 `414px` 宽
- 顶层页面 Frame：必须使用纵向 Auto Layout，宽度 `414px`
- 父级 Auto Layout：direction 为 `vertical`，padding-left 为 `0`，padding-right 为 `0`，item spacing 为 `16px`，horizontal alignment 为 `center`，height 为 hug contents 或按内容自适应。**若页面模式有明确的固定高度（如解释面板页的 414x896px），必须显式将顶层页面 Frame 的 `primaryAxisSizingMode` 或 `layoutSizingVertical` 设为 `FIXED` 以锁定物理高度，防止被自动布局收缩。**

这些参数只控制页面容器和组件实例之间的外部布局。不要为了满足这些数值而 detach 组件，或修改组件实例内部 Auto Layout、padding、gap、约束和样式。

所有 C 端模块必须作为同一个顶层页面 Frame 的直接子级，按页面模式或用户给定顺序从上到下排列，并在父级 Frame 内水平居中。普通卡片实例宽度使用 `382px` 或组件自身支持的内容区宽度；全宽头图、底部按钮及底部弹出面板（如 `Consumer/panel`）等保持 `414px`。禁止把模块插入后停留在同一坐标、使用绝对定位堆叠模块、手动随意拖拽间距，或让模块脱离顶层页面 Frame 的 Auto Layout。

## 内容填充规则

固定的是页面模块、组件顺序和组件使用关系，不代表每个模块的业务内容都是固定的。

props 内容优先级：

1. 用户明确提供的业务内容。
2. 已选参考页面或真实 Figma 组件中已有的默认内容。
3. 与字段含义一致的占位符，例如 `TODO：活动标题`、`待用户提供`。

不要为了让页面看起来完整而自行补充活动规则、奖励机制、版权声明、FAQ、用户数据或营销文案。若内容缺失，应该在 `component_gaps` 或 `validation.notes` 中说明需要用户补充。

## 最终产物

默认最终产物是 Figma 画布上的页面设计稿，而不是根目录下的 `*-spec.json` 文件。

页面规格 JSON 只在完整规格模式中作为中间产物，用于确认结构、组件映射和校验结果。生成 JSON 后必须继续执行画布搭建：创建 Frame、插入真实组件实例、填充 props、应用变体、排列模块顺序，并完成基础视觉检查。

不要因为已经生成 page spec 或内部组件清单就停止。除非当前环境没有 Figma MCP、Figma 插件或其他画布编辑工具，否则必须把设计稿实际搭到画布上。

## 完整规格结构

完整规格模式以 `assets/page-spec-schema.json` 作为标准 JSON 结构。至少包含：

- `audience_type`
- `requirement_summary`
- `matched_reference`
- `similarity_contract`
- `sections`
- `component_gaps`
- `validation`

每个 section 都必须包含对应端组件目录中完全一致的组件名、目标 Figma 组件引用、变体选择、props，以及相对匹配页面模式允许的差异。
